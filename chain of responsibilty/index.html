The idea

You send a request into a chain of handler objects. Each handler asks itself one question: "can I deal with this?" If yes, it processes it and the journey ends. If no, it forwards the exact same request to the next handler — and steps out of the story.

The caller only ever talks to the first handler. It has zero knowledge of how many handlers exist, or which one will eventually do the work. That's the decoupling this pattern is built for.

The code behind it

Same chain, written out

This is the exact chain the demo above is running — three handlers, one base class, one rule each.

leave-handler.ts 
// Step 1: shape of the request
interface LeaveRequest {
  employeeName: string;
  days: number;
}

// Step 2: base handler — the common contract
abstract class LeaveHandler {
  protected next: LeaveHandler | null = null;

  setNext(handler: LeaveHandler): LeaveHandler {
    this.next = handler;
    return handler;
  }

  handle(request: LeaveRequest): void {
    if (this.next) {
      this.next.handle(request);
    } else {
      console.log(`No one could approve ${request.employeeName}'s leave.`);
    }
  }
}

// Step 3: concrete handlers — check, or forward
class TeamLead extends LeaveHandler {
  handle(request: LeaveRequest): void {
    if (request.days <= 1) {
      console.log(`Team Lead approved it.`);
    } else {
      super.handle(request); // not mine — pass it on
    }
  }
}

// Manager and HR follow the same shape,
// each with its own threshold.

// Step 4: build the chain, once
const teamLead = new TeamLead();
const manager = new Manager();
const hr = new HR();
teamLead.setNext(manager).setNext(hr);

// Step 5: the client only ever calls the first link
teamLead.handle({ employeeName: "Kishan", days: 5 });

Field notes

Before you reach for it

✓USE WHEN

More than one object could handle a request, and you don't want a giant if-else deciding which one — or you want new handlers addable without touching old code.

✕AVOID WHEN

There's really only one handler and it'll never grow. A chain of one is just a function wearing a costume — skip the ceremony.

!COMMON MISTAKE

Forgetting to call the next handler when a handler can't process the request. The request quietly vanishes — no error, no trace. Always give the chain a fallback handler.

⇄DON'T CONFUSE WITH

Decorator. It also links objects, but every layer always runs and adds behavior. Here, a handler either owns the request fully or steps aside entirely.
